1. What is SQL Injection (SQLi)?
SQL Injection is a web security vulnerability that allows an attacker to interfere with the queries that an application makes to its database. It occurs when untrusted user input is directly concatenated or appended into a raw dynamic SQL query string instead of being treated as plain data.

2. How Can It Happen?
SQL Injection occurs when an application fails to properly sanitize, escape, or parameterize user input before executing a database command.

Vulnerable Code Example (Unsafe Dynamic Query)
Imagine an authentication query in Node.js/Express or PHP that constructs a query like this:

JavaScript
// DANGEROUS: Direct String Interpolation/Concatenation
const query = `SELECT * FROM users WHERE username = '${req.body.username}' AND password = '${req.body.password}'`;
db.query(query);
The Exploit
If an attacker submits the following input into the username field:

Plaintext
'admin' --
or
Plaintext
' OR '1'='1
The resulting SQL query executed by the engine becomes:

SQL
SELECT * FROM users WHERE username = 'admin' --' AND password = '...'
Because -- in SQL denotes a single-line comment, everything after admin' is completely ignored. The database executes SELECT * FROM users WHERE username = 'admin', logging the attacker in as admin without requiring a valid password.

3. Why Is It Dangerous?
SQL Injection is consistently ranked among the most severe web application risks (OWASP Top 10) due to its high impact:

Authentication Bypass: Attackers can log in as administrative users without credentials.

Data Exfiltration: Unintended access to confidential records (passwords, credit cards, personal identifiable information).

Data Corruption & Loss: Attackers can execute UPDATE or DROP TABLE commands to alter or destroy database contents.

Remote Code Execution (RCE): In certain database configurations (e.g., MySQL with INTO OUTFILE or PostgreSQL COPY), attackers can write malicious files to the underlying operating system and execute arbitrary shell commands.

4. How Do Prepared Statements Help?
Prepared Statements (also known as Parameterized Queries) separate the SQL code structure from the data inputs.

Compilation Phase: The database engine compiles and parses the SQL query skeleton first (e.g., SELECT * FROM users WHERE username = ? AND password = ?).

Execution Phase: The user input is bound to the placeholders (? or $1) strictly as literal scalar values—never executable code.

Even if an attacker inputs admin' -- or ' OR '1'='1, the database treats the entire input string literally as the actual username character by character, neutralizing the injection attack completely.

Safe Code Example (Parameterized)
JavaScript
// SAFE: Parameterized Query
const query = `SELECT * FROM users WHERE username = ? AND password = ?`;
db.execute(query, [req.body.username, req.body.password]);


5. What Other Database Security Practices Are Important?
	1. Principle of Least Privilege (PoLP):

		The database user account configured in your application should only possess the minimum required 		permissions (e.g., SELECT, INSERT, UPDATE, DELETE).

		Never connect your application using administrative accounts like root or sa.

	2. Input Validation and Sanitization:

		Validate user input against strict allow-lists (e.g., checking data types, string length, regex 		patterns) before it reaches the database driver.

	3. Password Hashing & Salting:

		Never store raw/plain-text passwords in a database. Use strong, slow password-hashing algorithms 		like bcrypt or Argon2 with unique per-user salts.

	4. Environment Variables for Credentials:

		Keep database credentials, hostnames, and secret keys out of source code repositories. Store them 		in .env files and access them via environment variables.

	5. Database Network Isolation & Firewalls:

		Ensure database servers are isolated inside private networks/VPCs and not exposed directly to the 		public internet. Restrict connections to trusted application server IP addresses.

	6. Error Handling & Information Leakage:

		Disable detailed database error messages in production. Raw database errors (e.g., syntax errors, 		column names) give attackers structural insights into your database schema.
